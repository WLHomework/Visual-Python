# 硬件积木库扩展实施计划

> 计划日期：2026-10-22  
> 依据：`docs/superpowers/plans/2026-10-21-block-toolbox-expansion.md`  
> 范围：先做 ESP32-S3 的硬件积木；WROOM/ESP8266 只在 S3 验证后做“可复用包”下放。  
> 本文是滚动计划：每完成一个工作包，更新实际完成日期和状态。

## 1. 目标与边界

### 1.1 本周期目标

1. 打通硬件模块积木的完整链路：积木 → 生成代码 → 设备端驱动 `/lib` 上传 → S3 真机运行。
2. 完成第一批 12 个 P0 能力（11 个新积木 + 现有 `hardware_tone`），让“传感器 / 执行器 / 显示”三个分类不再只有一两个积木。
3. 在不破坏现有 T6 功能的前提下，补一批高频 P1：存储、网络、SPI、串口和常用 I2C 传感器。
4. 给 WROOM/ESP8266 留下可复用接口，但不把未验证的积木直接铺到它们的工具箱。

### 1.2 不在本周期内

- Python 工具箱的大规模扩展。
- 摄像头、I2S 音频、AI 视觉等高级模块（BLE GATT 已按后续要求纳入 P2）。
- Mixly 积木的 1:1 复刻。
- 没有真实硬件时的“已验证”结论。

### 1.3 假设与前提

- 主开发板为 ESP32-S3-DevKitC-1，MicroPython v1.29.0。
- 真机冒烟测试需要用户提供板子、接线和桌面会话；硬件不可用时，静态开发继续，但里程碑标记为“阻塞”。
- 一次只做一个工作包，保持 `npm test` 和 `npm run build` 可回归。
- 除非明确要求，不提交、不推送。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| S3 真机不可用 | M3/M5 阻塞 | 静态开发继续；状态标阻塞，不宣称验证通过 |
| I2C 多设备冲突 | 传感器/OLED/LCD 互相影响 | 先完成共享 I2C 助手；接线和地址写入提示 |
| LCD1602 5V 电平 | 可能损坏输入或通信不稳 | 文档和积木提示明确要求电平转换/确认背板电压 |
| ESP8266 PWM/ADC 差异 | 代码在 8266 上读数/调速错误 | 生成器按板卡归一化；8266 单独真机验证 |
| 驱动太大 | ESP8266 RAM/Flash 不足 | 按需上传；一次只下放一个驱动；记录大小 |
| MicroPython API 不符 | 生成代码运行时报错 | 每个 API 按 v1.29 核对；标注“待核对”；真机确认 |
| 工具箱膨胀 | 分类滚动过长、查找困难 | 优先下拉式模块块；加小节标题；控制每批数量 |
| 新积木破坏 T6 | 网络/存储回归 | 每批跑全量测试；P0/P1 分阶段；不改现有语义 |
