## 迁移回归矩阵

| 场景 | 必须保持的行为 | 目标验证 |
| --- | --- | --- |
| Python 输出语句 | 按真实字段和输入槽生成并连接输出块 | 新计划一次提交、代码与工作区一致 |
| 嵌套动画结构 | 值积木使用真实连接检查器连接到动画输入 | 不兼容连接失败且不提交 |
| Turtle 语句链 | 语句块按计划顺序连接 | 连接顺序与生成代码一致 |
| 已有工作区局部编辑 | patch 只更改目标字段/连接/积木 | 未涉及的积木保持不变 |
| 不存在的字段或输入 | 返回操作序号和字段/输入名 | 原工作区与 commit 次数不变 |
| Python 生成校验失败 | 返回验证错误，不应用候选状态 | commit 调用次数为 0 |

## 上下文校验的范围（2026-10-18 修正）

原来的 `compose_workspace`（`compileBlockPlan`）对**整份候选工作区**做上下文校验：候选 = 用户工作区 + 本次改动，所以用户工作区里既有的、与本次改动无关的问题（切回本机目标后遗留的硬件积木、来自已禁用插件的旧积木、早就存在的必填输入缺失等）都会被算到这次计划头上，计划一律以 `CONTEXT_VALIDATION_FAILED` 失败。结果是：只要工作区里有一处历史问题，AI 就无法做任何修改，必须由用户先手工修好。

现在只把**本次计划创建或点名的积木**上的问题当作计划失败：

- 计划创建出来的积木（含模板里的影子块、`inputs` 里自动生成的字面量）——即创建积木及其全部子积木；
- 计划用 `blockId` / `afterBlockId` 点名的既有积木（`ref` 目标都是本次创建的积木，已包含在内）；
- 没有 `blockId` 的全局问题无法判断归属，仍然照常上报，避免放过真正的全局错误。

不在范围内的既有问题不再阻塞计划，但它们**仍然会显示在问题面板**（界面上的校验始终是全量的），所以不会被隐藏。计划报送的验证子集：

| 场景 | 期望 |
| --- | --- |
| 工作区里有无关的既有问题，计划只新增别的积木 | 成功提交（`ok: true`） |
| 计划自己创建的积木有上下文问题 | 失败，`CONTEXT_VALIDATION_FAILED`，并带回计划 `ref` |
| 计划自己创建的子积木（影子块/字面量）有问题 | 失败 |
| 计划按 `blockId` 修改的既有积木有问题 | 失败 |
| 无法定位到积木的全局问题 | 失败 |

测试：`src/agentV2/blockPlanCompiler.test.ts`（5 例）覆盖上表全部场景。

## 旧基线工具调用特征

- 现有测试验证 `compose_workspace` 的模板读取是单次批量调用。
- 多个旧写入工具仍可由执行器独立调用，因此模型选择路径并非唯一。
- 尚无真实模型端到端 Token/延迟基准；后续必须使用固定任务和模拟/记录的请求数据，不用未经测量的 Token 改善比例作为验收结论。
